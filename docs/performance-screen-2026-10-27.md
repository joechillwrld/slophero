# Gameplay performance screen, 2026-10-27

This screen uses the supplied v0.4.127 `Latest.log`, the already-supplied
symbolized 42-second WPA grid, the exact v1.1.0.6142 GameAssembly and resource
assets, and the current mod code. The log contains no presented-frame capture.
Callback counts, sampled inclusive CPU weights, and skipped setter counts are
different measurements; none establishes an FPS improvement by itself.

## Ranked, concrete follow-ups

| Lead | Evidence | Next code/measurement step |
| --- | --- | --- |
| Move song information from per-frame IMGUI to retained UI | Two 30-second runs with Song HUD on recorded 48,519 and 47,623 HUD repaints, averaging 0.010 ms each. A run with Song HUD off and Canvas counters still on recorded 266 HUD repaints. The song text is formatted at 5 Hz, but `DrawSongHud` repaints it on every rendered frame. This is roughly 0.48 seconds of measured mod callback CPU in the first run, before Unity GUI internals. | This build adds a separate default-off Canvas song HUD with the original IMGUI drag/resize and error fallback. It creates one more Canvas when on; that could offset the saved repaint work. Compare both CPU callback work and PresentMon presented intervals before enabling it by default or merging the two mod Canvases. |
| Remove the first active-song glow-hook setup hitch | In the first 30-second capture, the plain-held-glow switch logged activation 26 ms after the other song-scope activations, and `Core.OnUpdate` maxed at 28.480 ms. Timestamps suggest the activation contributes to the stall, although the log has no event-level attribution for that exact maximum. | This build prepares the inactive `Renderer.enabled` Harmony prefix at Gameplay initialization and caches the fixed 300-renderer glow population before song play or while paused, when the default-off switch is selected. If no idle window exists, the active path scans live. It still reads current enabled states and disables renderers on activation. Test a first song with/without the option and a pause/resume. |
| Push held-glow suppression into the native producer | The opt-in managed prefix blocked 9,080–14,471 redundant disable calls per song, and one song also blocked 3,241 re-enables. The exact GameAssembly has seven direct `Renderer.set_enabled` calls across the two specialized sustain helpers: RVAs `0x11559DB`, `0x1156127`, `0x115615F`, `0x11563BC`, `0x1156987`, `0x11569BF`, and `0x1156C33`, all targeting `0x2870FC0`. Four of these load false and three load true immediately before the call; branch ownership still needs full control-flow validation. | A guarded exact-build callsite patch could bypass only writes to confirmed glow renderer pointers before they enter the global managed setter. Do not patch one callsite in isolation: held, regular, and alternate branches differ. Verify every branch, register preservation, enable/disable restore, and clashes with other mods before a default-off Windows prototype. |
| Narrow regular-tail property-block traffic | The current default-off six-callsite native cache activated and skipped 0, 2,195, 3,734, 3,806, and 3,917 repeated submissions on different songs. This proves the producer sometimes repeats the same length; it does not reveal the cost per submission or prove the cache is faster. The exact shader disables instancing, so saving CPU writes is separate from reducing draw count. | Compare the same dense chart with the switch off/on in PresentMon and visually inspect tails, SP, whammy, and practice seeks. If it wins, map its remaining `GetPropertyBlock`/`SetFloat` sequence for a guarded short-circuit; do not extend it to dynamic held/open tails based on length alone. |

These weights overlap, and the stack export collapses renderer attribution. | Use the existing HUD/guitar camera isolation switches only as upper bounds, then isolate one actual layer-9 population (regular bodies, held glows, or effects) in otherwise matched frame captures. The earlier geometry batch was slower/visually risky; do not revive it without a draw-count or frame result. |
| Check retained Canvas rebuild work | The same WPA tree puts 732 ms inclusive in `UIEventsWillRenderCanvases` and 329 ms in `CanvasManager::RenderOverlays`; its `RenderCameras` branch is separate, so these numbers are not additive savings. Consolidating SlopHero song/counter text in one retained Canvas is a narrower test than hiding a game canvas or hand-batching its geometry. |
| Make hit/sustain particle suppression persistent | The pre-song live snapshots list 11 playing particle systems. `PerformanceOverrides.Apply` discovers the neck once and rechecks its particle objects once per second, stopping a target only when its GameObject is active. A game hit could reactivate an effect between checks, so the option may still allow brief simulation and rendering. The snapshot occurs before scope activation and does not prove which of the 11 are targets. | This build keeps each targeted effect's own Renderer disabled between checks and restores its prior state with the switch. An emitter could still simulate before the next stop pass. A broader CPU fix requires identifying actual reactivation; the generated `ParticleSystem.EmissionModule` lacks an `enabled` getter, so changing emission without a reliable restore value would be unsound. Avoid a global `Play` or `SetActive` hook. |
| Revisit whammy CPU/GPU work after producer attribution | The current dirty gate is installed and pass-through outside active solo; the exact game advances its CPU byte writer in 5 ms steps and uploads only when data changes under this switch.
